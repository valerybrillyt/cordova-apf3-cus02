# 3.8.1 Patrón de diseño

MVC, DAO y arquitectura de tres capas. Caso demostrado: CUS02, con acceso mínimo de CUS01.

Responsable de diseño: Nayu Valencia. Esta versión sustituye la propuesta Angular por la implementación JavaScript acordada y registra la etapa 6 con pruebas ejecutadas el 21 de noviembre de 2026.

## Etapa 1. Caso de uso

CUS02 registra un pedido de mesa o para llevar. Pertenece a PA01. El actor es el personal de atención. Cubre RF01 (solo mesa o para llevar en este caso), RF02, RF03 y RF04.

Precondiciones comprobadas: sesión de atención, catálogo leído desde MySQL y conexión activa.

Flujo implementado: modalidad, mesa si corresponde, uno o más productos con cantidad entera positiva, especificaciones permitidas, validación en el servidor y, solo después del `COMMIT`, el código real.

EA01 rechaza mesa vacía, pedido sin detalles, cantidad cero o negativa, producto inexistente, especificación incompatible y torta personalizada. No devuelve `idPedido`.

EA02 no confirma ni reintenta si la respuesta no llega. La idempotencia sigue pendiente: `docs/decisiones/PROPUESTA_IDEMPOTENCIA.md`.

CUS02 no cobra ni emite boleta.

## Etapa 2. MVC

La vista es `frontend/views/pedidos/registro.ejs` con `frontend/public/js/RegistroPedidoComponent.js`. `PedidosApiService.js` usa `fetch`. No hay SQL en el navegador.

El controlador es `backend/src/controllers/GestionPedidosController.js`, correspondiente a `C_GestionPedidos`. `registrarPedido` toma la sesión ya validada, llama a `procesarPedido` y responde JSON.

El modelo son `Pedido`, `DetallePedido`, `Producto` y `Especificacion`. `PedidoService.procesarPedido` concentra modalidad, mesa, cantidades, existencia del producto, especificaciones y autorización. No contiene SQL.

Flujo: vista, componente, servicio HTTP, `POST /api/pedidos`, controlador, servicio, modelos y DAO.

## Etapa 3. DAO

`Conexion.js` expone un pool `mysql2/promise` leído desde variables de entorno.

`ProductoDAO.listarProductos` y `consultarProducto` leen el catálogo real.

`PedidoDAO.registrarPedido` usa una conexión: `beginTransaction`, inserción de `pedido`, de cada `detalle_pedido`, de cada `especificacion`, y `commit` al final. Si falla, `rollback` y `release` en `finally`. `consultarPedido` queda para pruebas internas; no hay `GET /api/pedidos/:id`.

Las consultas usan `?`. La prueba guardó el texto `12' OR '1'='1` como número de mesa y las doce tablas siguieron existiendo.

## Etapa 4. Tres capas

Presentación: `frontend/`, EJS, JavaScript, Bootstrap 5.3.3 y CSS. Express sirve la vista y los estáticos en el mismo origen.

Negocio: `controllers/`, `services/`, `models/` y `validators/`.

Persistencia: `dao/`, `config/Conexion.js` y MySQL 8.0.40.

La demostración local usa una computadora. El diagrama de despliegue mantiene dos nodos de servidor como propuesta.
